# Agent Note: TUI 读取滚轮并在轮次进行中保持键盘可用

Status: implemented

[English](2026-09-18-tui-wheel-scrolling-and-streaming-input.md) | 中文

## 问题

在未开启鼠标上报的备用屏幕中，终端把滚轮转换为光标键。输入框把这些按键当作提示词历史，因此滚动会用较早的提示词替换草稿，而不是移动对话，读者也完全无法用滚轮跟随正在进行的轮次。另外，每个流式 token 都会通知一次存储变更并重新布局整条不断增长的消息；在较长的 transcript（文本记录）上，这一开销超过 token 之间的间隔，导致回答生成期间输入框无法接收按键。正在进行的提交也会在准入结束前吞掉所有按键。

## 决策

应用在 Ink 接管备用屏幕后开启带 SGR 坐标的按钮事件上报（`1002`/`1006`），并在组件卸载时交还鼠标处理，覆盖运行器已经通过 `ink.unmount()` 驱动的所有退出路径。`mouse.ts` 把一次输入事件分类为滚轮刻度、按钮或拖动上报，或旧式 X10 前缀；按键处理器每个刻度滚动三行，按住 Ctrl 时滚动一页，把未带修饰键的主按钮按下与拖动交给应用内操作和文本选择，并丢弃其他所有上报，确保坐标字节不会进入提示词。滚轮滚动使用既有的条目相对锚点，因此在模型输出期间同样可用，并在到达最后一行时重新跟随实时末尾。由于上报会让终端自身的点击和拖动选择失效，`/mouse off` 和 `DSH_TUI_MOUSE=off` 可在本会话中交还这两项操作。

流式 token 会立即并入 transcript，但每帧只通知一次重绘；文档复用消息中已完成各行的渲染行：Markdown 在代码围栏外的空行处完成，推理内容在任意换行处完成，其他条目、宽度变化或改写一律回退为完整布局。换行处理已排版好的行不会再次转义和分段。在包含 240 个条目、其中一条消息增长到 16,000 字符以上的 transcript 上，单次重绘的平均耗时从 544 ms 降至 3 ms，并且测试断言每个前缀的渲染行都与完整布局完全一致。提示词处于准入阶段时仍可输入；只有发送锁阻止第二次提交，准入期间编写的草稿会被保留。

## 考虑过的替代方案

按时间检测滚轮形态的光标键连发被否决：它无法与按住方向键区分，而且终端的滚轮行为仍只有输入框的历史回溯。永久开启上报且不提供退出方式被否决，因为对部分用户而言，从对话中复制文本比滚轮更重要。仅限制重绘频率并不足够：布局开销随消息长度增长，长回答仍会占满每一帧。在 `wrapProse` 和 `markdownRows` 内部实现增量换行可以达到比行更细的粒度，但回放和窗口缩放也使用这两个函数；复用已完成的整行能让流式文本与回放文本共用同一种布局。

## 后果

滚轮上报开启时，点击或拖动由应用消费；大多数终端仍可按住 Shift 进行选择，帮助面板和 README 都说明了这一点。忽略 `1006` 的终端会以 X10 编码上报，其坐标字节会被丢弃而不会被输入，但这些终端无法滚动。合并的变更会立即对 `getState` 可见，并在一帧内显示到屏幕上，因此重绘可能比 token 滞后最多一帧；任何即时变更都会连同已合并的变更一起通知。流式布局一次只为一个条目保留渲染行，因此两条消息同时增长时会在复用与完整布局之间交替。本记录所依赖的终端原生呈现决策见 [TUI Agent Note](../feature/2026-09-18-terminal-native-tui.zh.md)。
